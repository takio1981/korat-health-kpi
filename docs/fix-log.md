## 2569-10-23 — ตารางสรุป (kpi_summary) ของกราฟ/รายงาน อัปเดตอัตโนมัติทันทีหลังบันทึกผลงาน

### ความต้องการ
- เดิมเฉพาะผลงานข้อย่อย/กิจกรรมที่อัปเดต summary ทันที — ผลงานหลัก (`/update-kpi`) การอนุมัติ/ส่งกลับ/ปลดล็อค/อุทธรณ์ ต้องให้ผู้ดูแลกด "อัปเดต Summary"
  กราฟ รายงาน และการ์ดสถิติจึงไม่ตรงกับหน้าบันทึกผลงานจนกว่าจะกด — ผู้ใช้ต้องการให้อัปเดตทันที

### การแก้ไข
- `scheduleSummaryRefresh()` = คิวต่อคู่ (ตัวชี้วัด × ปีงบ) แบบเบื้องหลัง: ไม่หน่วงการตอบกลับ, คู่เดียวกันไม่รันซ้อน, บันทึกระหว่างรัน → รันซ้ำรอบเดียว —
  เรียกหลัง `/update-kpi` ทุกโหมด, approve/reject/unlock/unlock-all/appeal/appeal-approve/appeal-reject/reply-kpi/mark-read (Resubmit), `/dynamic-data` sync,
  ข้อย่อย/กิจกรรม (เดิม) และ PUT `/indicators`
- refresh รันบน connection READ COMMITTED (ไม่ถือ lock แถวผลงาน — ไม่บล็อกการบันทึกของผู้ใช้คนอื่น) + ลองใหม่เมื่อ deadlock/ชนคีย์
- **บั๊กที่พบระหว่างทำ:** กด "อัปเดต Summary" ขณะคิวอัตโนมัติทำงาน → `/refresh-summary/batch` ชน `uk_ind_year_hos` (batch ไม่ลบก่อน INSERT พึ่ง prepare ลบทั้งปีไว้)
  — ชุดทดสอบเดิม 3 ชุดล้ม 18 กรณีหลังเปิดอัปเดตอัตโนมัติ → แก้: batch ลบแถวของตัวชี้วัดชุดนั้นก่อน INSERT + `withSummaryLock()` ให้คิว/prepare/batch/finalize/ลบผลงานแบบชุดทำทีละงาน
- แก้ข้อความ "ผ่านเกณฑ์ = ผลงานล่าสุด ≥ เป้าหมาย" ที่ค้างในหน้ากราฟและคู่มือ (ตกหล่นจากงานเงื่อนไขเป้าหมาย 22 ต.ค.)
- ตรวจฐานจริงก่อน (อ่านอย่างเดียว ตามหัวข้อ 9.4): kpi_summary 849 แถว มี unique key ครบ ไม่มีคู่ใน summary ที่ไม่มีแถวใน kpi_results → refresh รายคู่ปลอดภัย

### ทดสอบ
- API 27 ชุด 275 กรณี (ใหม่ `summary-auto-refresh.test.js` 4 กรณี — ล้มทั้ง 4 กับโค้ดเดิม; รวมเคสสั่ง refresh คู่เดียวกันพร้อมกัน 7 ครั้ง + แก้ข้อมูลระหว่างรัน) รันซ้ำ 2 รอบผ่าน
- หน้าจอจริง (backend 3710 → khups_kpi_test_db): บันทึกผลงานจากหน้าบันทึกผลงาน → kpi_summary มีผลงานทันทีโดยไม่กดปุ่ม, หน้ารายงานสถิติแสดงผ่าน 1/1,
  อนุมัติ → summary เป็น Approved/ล็อค — ลบข้อมูลทดสอบแล้ว
- ไม่ครอบคลุม (ตั้งใจ): `/bulk-add-kpi` (เพิ่มเฉพาะเป้าหมาย summary ไม่เก็บ), `/clear-kpi-data` (ลบทั้งหมด — คงพฤติกรรมเดิม)

## 2569-10-22 — เงื่อนไขเป้าหมาย (≥ > ≤ < =): ร้อยละ/ผ่านเกณฑ์ในตารางบันทึกผลงาน รายงาน และกราฟ

### ปัญหา
- `kpi_indicators.target_condition` มีอยู่แล้ว (ข้อมูลจริง: GTE 156, EQ 7, LTE 5, LT 4, GT 2) แต่**ไม่เคยถูกใช้คำนวณ** — หน้าบันทึกผลงานคิดร้อยละ = ผลงาน ÷ เป้าหมาย
  และผ่าน = ผลงาน ≥ เป้าหมาย เสมอ; backend นับ "ผ่าน" ด้วย `last_actual >= target_value` ซ้ำหลายจุด → ตัวชี้วัด "ยิ่งน้อยยิ่งดี" เช่น
  อัตราตาย ≤ 8 ผลงาน 4 แสดง 50% สีแดงและนับว่าไม่ผ่านในการ์ด/รายงาน/กราฟ
- `GET /kpi-results` ไม่ได้ส่ง `target_condition` → ป้ายเกณฑ์ข้างชื่อตัวชี้วัดในหน้าบันทึกผลงานไม่เคยมีสัญลักษณ์ (พบระหว่างทดสอบหน้าจอ)
- dropdown และการตรวจไฟล์นำเข้ารองรับแค่ GTE/LTE/EQ (ข้อมูลจริงมี GT/LT จาก KHD)

### การแก้ไข (ผู้ใช้เลือกวิธีคิด)
- กฎกลาง `kpi-target` (2 สำเนา + fixture ร่วม 37 กรณี): ≥ > = ผลงาน ÷ เป้าหมาย | ≤ < = เป้าหมาย ÷ ผลงาน (ผลงาน 0 = 100%) | = = ค่าน้อย ÷ ค่ามาก
- SQL `targetHasSql`/`targetPassSql` แทนทุกจุดที่นับผ่าน (การ์ด + อันดับ, รายงาน 4 แถบ, chart-stats รวมรายเดือน) — อ่านเงื่อนไขสด ไม่ต้อง refresh summary
- หน้าแก้ไขตัวชี้วัด: เงื่อนไข 5 แบบ + คำอธิบาย/ตัวอย่าง, "วิธีคิดผลงาน" สำเร็จรูป (ทางลัดของสะสม/สูตรเดิม) — หน้าบันทึกผลงาน: สัญลักษณ์หน้าเป้าหมาย
- ข้อมูลจริงที่ได้รับผลทันทีหลัง deploy: ตัวชี้วัดเปิดใช้งาน LTE 3 / LT 4 / EQ 5 / GT 2 ตัว (GTE/ไม่ระบุ ผลเท่าเดิม)

### ทดสอบ
- API 26 ชุด (ใหม่ `kpi-target.test.js` 38, `target-condition.test.js` 6 — 5 กรณีล้มกับโค้ดเดิม), Frontend 23 ชุด 273 กรณี, `ng build` ผ่าน
- หน้าจอจริง (backend 3710 → khups_kpi_test_db, บล็อกการเชื่อมต่อออก): ตัวชี้วัด ≤ 8 — กรอก 4 → ≤8 / 200% เขียว, กรอก 10 → 80% แดง, บันทึก;
  หน้าแก้ไขตัวชี้วัดแสดง 5 เงื่อนไข + คำอธิบาย เลือก "ค่าเฉลี่ย" → บันทึก AVG(ALL); อัปเดต Summary → ผลงาน 7, รายงานรายตัวชี้วัดนับผ่าน 1/1,
  หน้าบันทึกผลงาน 7 = 114.29% เขียว — ลบข้อมูลทดสอบแล้ว
- หมายเหตุ (การออกแบบเดิม ไม่ได้เปลี่ยน): บันทึกผลงานหลักที่หน้าบันทึกผลงานไม่ refresh `kpi_summary` อัตโนมัติ (ใช้ปุ่มอัปเดต Summary) ต่างจากการบันทึกข้อย่อย/กิจกรรม

## 2569-10-20 — ตัวชี้วัดหลายระดับแบบต้นไม้ (4 ระดับ ขยายได้)

### ความต้องการ
- เพิ่มระดับต่อจากตัวชี้วัดย่อยอีก 1 ระดับ รวม 4 ระดับ หรือออกแบบให้เพิ่มได้อีกในอนาคต — ผู้ใช้เลือก: ระดับใหม่อยู่ระหว่างย่อยกับกิจกรรม
  (หลัก 1 → ย่อย 1.1 → ย่อยระดับ 2 1.1.1 → กิจกรรม 1.1.1.1) แบบต้นไม้ยืดหยุ่น

### การแก้ไข
- `kpi_sub_indicators.parent_sub_id` (FK ตัวเอง CASCADE) — ทุกข้อเก็บ `indicator_id` ของหลักเหมือนเดิม การอนุมัติ/ล็อค/ลบ/สถิติเดิมครอบคลุมทุกระดับทันที
- `kpi_hierarchy_max_levels` (ตั้งค่าระบบ 3–6 ค่าตั้งต้น 4) — `POST /sub-indicators` / `/sub-activities` ตรวจระดับ + ข้อแม่ต้องเป็นตัวชี้วัดเดียวกัน
- `rollupTree()` + `isRolledNode()` (kpi-rollup 2 สำเนา + fixture `tree` 6 กรณี) แทนกฎ "auto + มีกิจกรรม" ที่เขียนซ้ำ 4 จุด
- dashboard (แถวลูกเยื้องตามระดับ), หน้าต่างบันทึกผลงานย่อย, kpi-manage (ต้นไม้ + ปุ่ม "+ ข้อย่อย"), Export `_items` (item_kind + PK ใหม่ + ย้ายตารางเดิม)
- ข้อมูลจริง (อ่านอย่างเดียว): ข้อย่อย 18 ข้อ ผลงาน 2,376 แถว กิจกรรม 0 → ทั้งหมดเป็นระดับบนสุด พฤติกรรมเดิมไม่เปลี่ยน

### บั๊กที่แก้ร่วม
- `DELETE /sub-indicators/:id` เดิมลบข้อที่มีผลงานได้และ CASCADE ลบผลงานเงียบๆ → ปฏิเสธ (400) ถ้าข้อนี้/ข้อลูก/กิจกรรมใต้ลงไปมีผลงาน
- ชุดทดสอบ API ล้มแบบสุ่มคนละไฟล์ทุกรอบ (error-monitoring / data-entry-lock / session) — สาเหตุ "Too many connections": แต่ละไฟล์สร้าง pool ใหม่
  (limit 150, idle 5 นาที) เกิน max_connections 151 ของ MariaDB ที่ใช้ร่วมกับระบบจริง → `tests/setup.js` ตั้ง pool เล็ก (20 / maxIdle 2 / idle 2 วินาที)
  + `db.js` อ่าน `DB_POOL_IDLE_TIMEOUT` (ค่าระบบจริงไม่เปลี่ยน) — รันซ้ำ 3 รอบผ่านครบ

## 2569-10-12 — ตัวชี้วัดย่อย: ไม่ต้องกรอกครบทุกข้อทุกเดือน (ยกยอดผลงานล่าสุดของแต่ละข้อ)

### ความต้องการ
ผู้ใช้ต้องการลดการบันทึกผลงานตัวชี้วัดย่อย: ข้อที่ผ่านแล้วไม่ต้องกรอกซ้ำทุกเดือน ให้กรอกเฉพาะข้อที่ยังไม่ผ่าน แล้วให้ระบบนำผลงานของ
แต่ละข้อไปคำนวณผลงานรวมและค่าเฉลี่ยแทน — เดิม (11 ต.ค.) ข้อที่ไม่ได้กรอกในเดือนนั้นถูกนับเป็น 0 ทำให้ต้องกรอกทุกข้อทุกเดือนผลงานจึงจะไม่ตก

### การแก้ไข
- `loadSubAggregates()` (api/server.js): ไล่เดือนตามปีงบ (ต.ค. → ก.ย.) เก็บผลงานล่าสุดของแต่ละข้อ ค่ารายเดือน = ผลรวมผลงานล่าสุดของทุกข้อ ณ เดือนนั้น ÷
  จำนวนข้อย่อยที่เปิดใช้งานทั้งหมด (ข้อที่ยังไม่เคยกรอก = 0) — เดือนที่ไม่มีข้อใดกรอกเลยยังเว้นว่างเหมือนเดิม ไม่ยกยอดข้ามปีงบ
  → มีผลกับหน้าบันทึกผลงาน, Export KPI และการตรวจการเปลี่ยนแปลงก่อน Export พร้อมกัน (ใช้ฟังก์ชันเดียวกัน)
- `POST /sub-results/upsert`: เก็บเลข 0 (ชนิดตัวเลข) เป็น 0 จริง ไม่แปลงเป็นค่าว่าง — การกรอก 0 มีความหมายแล้ว (ทับค่าที่ยกยอดมา)
- หน้าต่างบันทึกผลงานตัวชี้วัดย่อย: `getSubMonthlyAggregates()` ตรรกะเดียวกับ backend, การ์ด "ผลงานรวม" ใช้ค่านี้, เพิ่มแถว "ผลงานรวมรายเดือน"
  ท้ายตาราง และข้อความแนะนำใต้ตาราง

### ตัวอย่าง
3 ข้อย่อย: ต.ค. กรอก ข้อ1 = 90, ข้อ2 = 60 → ต.ค. = 50 | พ.ย. กรอกเฉพาะข้อ3 = 30 → พ.ย. = (90 + 60 + 30) ÷ 3 = 60 (เดิมได้ 10)

— API 145 / Frontend 156 ผ่านทั้งหมด

ข้อมูลผลงานย่อยที่บันทึกไว้เดิมไม่ถูกแก้ไข แต่ผลงานรายเดือนของตัวชี้วัดหลักที่คำนวณจากข้อย่อยจะเปลี่ยนตามกติกาใหม่ทันที

## 2569-10-11 — เพิ่มตัวชี้วัดให้ง่ายขึ้น: รหัสอัตโนมัติ, ตรงประเภทหน่วยบริการที่ตั้งไว้, ป้ายสูตรทุกหน้า

### ความต้องการ
1. หน้าจัดการตัวชี้วัด — เพิ่มข้อมูลใหม่ ผู้ดูแลไม่รู้ว่า "รหัสอ้างอิง (เช่น 1901)" / "รหัสตัวชี้วัด" ต้องกรอกอะไร
2. หน้าบันทึกผลงาน — การเพิ่มตัวชี้วัดให้หน่วยบริการต้องง่ายขึ้น และรายการหน่วยบริการต้องตรงกับประเภทหน่วยบริการที่ตั้งไว้ในตัวชี้วัด
3. ตัวชี้วัดที่ตั้งสูตรไว้ ให้แสดงไอคอนและสูตรในทุกหน้าที่มีรายชื่อตัวชี้วัด

### สิ่งที่พบจากข้อมูลจริง (174 ตัวชี้วัด)
- "รหัสอ้างอิง" ตรงกับเลขรายงานของ KHD 134 ตัว ว่าง 8 ตัว → เป็นข้อมูลของตัวชี้วัดที่มาจาก KHD ไม่ใช่สิ่งที่ผู้ใช้ต้องคิดเอง
- "รหัสตัวชี้วัด" = ชื่อตาราง (table_process) แบบขีดกลาง → สร้างจากชื่อตารางได้
- ไม่กรอกชื่อตาราง = บันทึก NULL → ตัวชี้วัดส่งออก/สร้างฟอร์มไม่ได้จนกว่าจะกลับมาแก้
- หน้าต่างเพิ่มตัวชี้วัดให้หน่วยบริการ: เปิดมาติ๊กทุกตัวให้, ไม่มีช่องค้นหา, ตาราง 12 เดือนกว้างมาก, เปลี่ยนตัวกรองแล้วค่าที่กรอกหาย,
  และ**ไม่สนใจประเภทหน่วยบริการที่ตั้งไว้ในตัวชี้วัด** (เพิ่มตัวชี้วัดของ รพ.สต. ให้โรงพยาบาลได้ ทั้งหน้าจอและ API)

### วิธีแก้
- **รหัสอัตโนมัติ:** `suggestIndicatorCodes()` + `GET /indicators/suggest-code` + `POST /indicators` สร้างรหัสเมื่อไม่กรอก

## 2569-09-26 — แก้เมนู slide มือถือบางหน้าบางครั้งกดแฮมเบอร์เกอร์แล้วไม่ขึ้นเมนู

### คำขอ

### สาเหตุที่ยืนยันจากการอ่านโค้ดจริง
- `layout.ts` ใช้ตัวแปร **`isSidebarOpen` ตัวเดียวกัน** ควบคุมทั้ง 2 เรื่องที่ไม่เกี่ยวข้องกัน:

  กลไกนี้ออกแบบมาสำหรับจอใหญ่ (ให้พื้นที่แก้ไขเต็มจอ) แต่เพราะแชร์ตัวแปรเดียวกับเมนู slide มือถือ การเข้า-ออก
  โหมดแก้ไขบนจอมือถือจึงไปเขียนทับค่า `isSidebarOpen` ที่จริงๆ ควรถูกควบคุมด้วยปุ่มแฮมเบอร์เกอร์เท่านั้น ทำให้
  บางจังหวะเมนู slide เปิดเองโดยไม่มีใครกด หรือค่าที่ควรจะกลับมาเปิดได้ไม่ตรงกับที่ผู้ใช้กดจริงอีกต่อไป

  สลับกับเปิดเมนู) ยืนยันว่า pattern การใช้ตัวแปรร่วมกันนี้เป็นจุดเสี่ยงจริงที่ทำให้สถานะเพี้ยนได้ในบางจังหวะ แม้จะ
  ไม่สามารถ pin จังหวะที่แน่นอน 100% ที่ผู้ใช้เจอ แต่เป็นสาเหตุเชิงสถาปัตยกรรมที่ชัดเจนและแก้ได้ตรงจุด

### วิธีแก้
แยกตัวแปรควบคุมเมนู slide มือถือออกมาต่างหาก (`isMobileMenuOpen`) ไม่ให้ใช้ร่วมกับ `isSidebarOpen` อีกต่อไป:

## 2569-09-26 — แก้เมนู slide บนมือถือถูกกล่องตัวกรองทับ กดเลือกเมนูไม่ได้

### คำขอ
หน้า dashboard บันทึกผลงานตัวชี้วัด กล่องตัวกรองซ้อนทับเมนู slide (มือถือ) ทำให้เลือกเมนูไม่ได้ — พร้อมภาพหน้าจอ
ประกอบ (มือถือ กดปุ่ม hamburger เปิดเมนูแล้วเห็นกล่องตัวกรองทับอยู่ด้านบน ไม่ดำมัวเหมือนพื้นหลังปกติ)

### สาเหตุที่ยืนยันจากการอ่านโค้ดจริง
- Layout mobile menu (`layout.html`): ฉากหลังมืด (backdrop) เดิม `z-40`, กล่องเมนู slide เดิม `z-50`
- Dashboard filter wrapper (`dashboard.html:9`) เป็น `sticky top-0 z-50` (ถูกปรับจาก z-30 เป็น z-50 ในงานก่อนหน้า
  เพื่อให้สูงกว่าหัวตาราง frozen ที่ z-40 ใน `dashboard.css`) — ทำให้ z-index **เท่ากับ** เมนู slide ของ layout พอดี
- เมื่อ z-index เท่ากัน กติกา CSS จะให้ธาตุที่มาทีหลังใน DOM ทับอยู่บน — กล่องตัวกรองของ dashboard (routed content)
  render หลังเมนู slide ของ layout เสมอ จึงทับเมนูจนกดไม่ทะลุ และเพราะตัวกรองมี z-index สูงกว่าฉากหลังมืด (z-40)
  ด้วย มันเลยไม่ถูกทำมืดแบบพื้นหลังปกติ (เห็นสว่างชัดทับอยู่)
- ตรวจแล้วพบว่ามีอีก 15 หน้าที่ใช้ pattern `sticky ... z-50` แบบเดียวกัน (kpi-manage, user-management,
  announcements, notifications, feedback, report ฯลฯ) — เป็นปัญหาเชิงระบบ ไม่ใช่แค่หน้า dashboard เดียว

### วิธีแก้
แก้ที่ระดับ layout (จุดเดียว ครอบคลุมทุกหน้า) แทนที่จะไล่ลด z-index ทีละหน้า:
- backdrop มืด: `z-40` → `z-[60]`
- กล่องเมนู slide: `z-50` → `z-[70]`
- header (ที่มีปุ่ม hamburger): `z-40` → `z-[65]` (ต้องยกตามด้วย ไม่งั้น backdrop ใหม่จะทับ header จนมืดไปด้วย
  ทั้งที่ header ต้องเห็น/กดได้ตลอดเวลาเพื่อปิดเมนู)
- ตรวจแล้วว่า z-index สูงสุดที่มีอยู่จริงในทุกหน้า (`dashboard.css` frozen header = 40) ยังต่ำกว่าค่าใหม่ทั้งหมด
  จึงไม่กระทบ dropdown/sticky อื่นๆ ที่มีอยู่เดิม
- ทดสอบผ่าน dev server + Playwright ที่ mobile viewport (390×844): เปิดเมนู → กล่องตัวกรองถูกทำมืดถูกต้อง →
  กดลิงก์เมนูสำเร็จ (navigate ไปหน้าอื่นได้จริง ไม่ใช่แค่มองเห็นแต่กดไม่ทะลุเหมือนเดิม)

## 2569-09-25 — ออกแบบกล่อง "เข้าสู่ระบบ" ใหม่ ป้องกันเนื้อหาล้นออกนอกกล่อง

### อาการที่พบ
ผู้ใช้งานแจ้งว่ากล่อง "เข้าสู่ระบบ" หน้า login ไม่พอดี — ช่องกรอกชื่อผู้ใช้งาน/รหัสผ่าน หรือปุ่มต่างๆ ไม่อยู่ในกล่อง
(ล้นออกนอกขอบเขตกล่อง)

### สาเหตุ
กล่อง login (glassmorphism card) ใช้ `max-h-[90vh] overflow-y-scroll` เพื่อจำกัดความสูงบนจอที่มีพื้นที่จำกัด
แต่ระยะห่าง (padding/margin) ภายในกล่องเดิมกว้างเกินไป เมื่อรวมทุกส่วน (หัวข้อ, ปุ่มลงทะเบียน/คู่มือ, ช่องชื่อผู้ใช้งาน,
ช่องรหัสผ่าน, ปุ่มเข้าสู่ระบบ, ปุ่ม ThaID + ProviderID พร้อมสถานะเชื่อมต่อ) ความสูงเนื้อหาจริงรวมแล้วประมาณ **744px**
ในขณะที่หน้าจอแล็ปท็อปทั่วไป (เช่น 1366×768 หักลบพื้นที่แถบเครื่องมือเบราว์เซอร์แล้วเหลือใช้งานจริงประมาณ 650px)
กล่องจะถูกจำกัดไว้ที่ 90vh (~585px) ทำให้ปุ่ม ProviderID และข้อความท้ายกล่องถูกซ่อนเลยขอบล่าง ต้องเลื่อน (scroll)
ภายในกล่องเพื่อดู ซึ่งผู้ใช้จำนวนมากไม่สังเกตว่าเลื่อนได้ (scrollbar บางและจางมาก)

ตรวจสอบด้วย headless browser (Playwright) ยืนยันตัวเลขจริง: ที่ viewport 1366×650 — `scrollHeight: 744px`,
`clientHeight: 585px` (`overflowing: true`)

### วิธีแก้
ปรับลดระยะห่าง/ขนาด (padding, margin, gap) ภายในกล่องทั้งหมดให้กระชับขึ้นแบบเป็นระบบ โดยไม่เปลี่ยนโทนสี/สไตล์เดิม —
ไฟล์ `frontend/src/app/login/login.html`:
- กล่องหลัก: `p-7 sm:p-9` → `p-5 sm:p-6`, เปลี่ยน `overflow-y-scroll` → `overflow-y-auto` (แสดง scrollbar เฉพาะตอนจำเป็นจริงๆ)
- หัวข้อ "เข้าสู่ระบบ": ลด font size + margin (`text-3xl`→`text-2xl`, `mb-7`→`mb-3.5`)
- แถวปุ่มลงทะเบียน/คู่มือ: ลด padding ปุ่ม + margin
- ฟอร์ม: `space-y-5`→`space-y-3`, label `mb-2`→`mb-1`, input `py-3`→`py-2.5`, ปุ่มเข้าสู่ระบบ `py-3`→`py-2.5`
- ส่วน SSO (ThaID/ProviderID): ลด margin หัวข้อคั่น, ปุ่ม `py-3`→`py-2`, ไอคอนโลโก้ `h-7`→`h-6`, ย่อข้อความอธิบายให้สั้นลง
  พร้อมเพิ่ม `truncate` กันข้อความยาวตกบรรทัดบนจอแคบ

ตรวจสอบซ้ำด้วย Playwright ที่ viewport เดิม (1366×650) หลังแก้ไข: `scrollHeight: 586px`, `clientHeight: 586px`
(`overflowing: false`) — พอดีกล่องทั้งหมด **ไม่ต้องเลื่อนอีกต่อไป** แม้เปิดใช้งานทั้ง ThaID และ ProviderID พร้อมกัน
ทดสอบเพิ่มเติมที่ 1440×900, 390×844 (มือถือ), 320×568/760 (จอแคบสุด) ยืนยันว่าองค์ประกอบทั้งหมดยังคงอยู่ในกล่อง
ไม่ล้น ไม่ทับกัน และไม่ดูอัดแน่นจนเกินไป

## 2569-09-25 — แจ้งเตือน "ผู้ใช้งานใหม่รอการอนุมัติ" ค้างในระบบ กดแล้วขึ้น 404

### อาการที่พบ
Console แสดง error 2 รายการ:
```
idle-timeout.service.ts:25  GET .../khupskpi/api/settings 401 (Unauthorized)
notifications.ts:381  GET .../khupskpi/api/users/57/basic 404 (Not Found)
```

### สาเหตุ

**1. `/settings` 401 (idle-timeout)** — ไม่ใช่บั๊กใหม่ เป็นผลข้างเคียงที่รู้อยู่แล้วจากการแก้ไขก่อนหน้า (commit `4c095999`)
ที่บังคับให้ `/settings` ต้อง login ก่อนถึงจะเรียกได้ — บราวเซอร์จะ log request ที่ยิงตอนแอปเพิ่งเปิด (ก่อน login)
เป็น network error เสมอไม่ว่าแอปจะออกแบบยังไงก็ตาม ไม่กระทบผู้ใช้งานจริงเพราะระบบดึงค่าซ้ำอีกครั้งหลัง login สำเร็จแล้ว

**2. `/users/57/basic` 404 (สาเหตุหลัก ต้องแก้จริง)** — เมื่อผู้ใช้งานถูกลบออกจากระบบ (3 จุดที่มีการ `DELETE FROM users`
ใน `api/server.js`: ลบ account เก่าตอนสมัครซ้ำด้วย CID เดิม, ลบ account เก่าตอนสมัครซ้ำด้วย username เดิม, และ
`DELETE /users/:id` ที่ admin กดลบเอง) ระบบไม่เคยลบ notification "ผู้ใช้งานใหม่รอการอนุมัติ" ที่อ้างอิงถึงผู้ใช้งาน
คนนั้นไปด้วย (`notifications.created_by = <user id ที่ถูกลบ>`) ทำให้ Super Admin เห็นแจ้งเตือนค้างอยู่ในกระดิ่ง
แจ้งเตือนตลอดไป พอกดเข้าไปดูรายละเอียด frontend เรียก `GET /users/:id/basic` ด้วย id ที่ไม่มีอยู่แล้ว → 404

ตรวจสอบฐานข้อมูล dev พบว่าปัญหานี้สะสมมานานแล้ว มีแจ้งเตือนค้างลักษณะนี้อยู่ **78 รายการ** สำหรับ Super Admin
(user_id = 6) อ้างอิง user id ตั้งแต่ 55 ถึง 140 ที่ถูกลบไปแล้วทั้งหมด

### วิธีแก้

เพิ่มฟังก์ชัน `cleanupPendingApprovalNotifications(deletedUserId)` ใน `api/server.js` (ต่อจาก `sendLineToUser`):

```javascript
async function cleanupPendingApprovalNotifications(deletedUserId) {
    try {
        if (!deletedUserId) return;
        await db.query(
            "DELETE FROM notifications WHERE title = 'ผู้ใช้งานใหม่รอการอนุมัติ' AND created_by = ?",
            [deletedUserId]
        );
    } catch (e) {
        console.error('[cleanupPendingApprovalNotifications] failed:', e.message);
    }
}
```

เรียกใช้ทันทีหลัง `DELETE FROM users` ทั้ง 3 จุด:
1. `/register` — cleanup account เก่าที่ถูกปฏิเสธ (ตรวจซ้ำด้วย cid)
2. `/register` — cleanup account เก่าที่ถูกปฏิเสธ (ตรวจซ้ำด้วย username)
3. `DELETE /users/:id` — admin ลบผู้ใช้งานเอง

**เหตุผลที่ใช้ `title` เจาะจงแทน `created_by` เฉยๆ:** คอลัมน์ `created_by` ในตาราง `notifications` ถูกใช้ร่วมกับ
notification ประเภทอื่นอีกกว่า 15 จุด (KPI approve/reject/appeal, target request ฯลฯ) การลบแบบ blanket ด้วย
`created_by` อย่างเดียวจะทำลายประวัติแจ้งเตือนที่ไม่เกี่ยวข้องไปด้วย จึงต้อง match ด้วย title ที่เจาะจงเฉพาะ
"ผู้ใช้งานใหม่รอการอนุมัติ" เท่านั้น

พร้อมทำ one-off cleanup ลบแจ้งเตือนค้างเก่า 78 รายการที่มีอยู่แล้วในฐานข้อมูล (dev/prod ใช้ DB เดียวกัน
ผ่าน `host.docker.internal`) ยืนยันว่าเหลือ 0 รายการหลังลบ
